# 一段特征表达式，是怎么变成一次线上结果的

这篇文档用大白话讲清楚 Feature DAG 引擎的分层设计：每一层解决什么问题、彼此怎么交接，
以及贯穿全链路的一条核心原则——把"想清楚"和"做出来"这两件事，彻底分开。

如果你想看更贴近源码、带精确文件行号引用的版本，见
[`system-architecture-overview.md`](system-architecture-overview.md)；本文侧重理解，那一篇侧重查阅。

## 核心思想：先想清楚，再照着做

这套系统把"要算什么、按什么顺序算、能不能省点计算量、要不要缓存"这些决策，尽量都提前在服务启动的那一刻
做完；等到真正处理一次线上请求的时候，它只是照着一份写死的执行清单，机械地跑一遍，不再临时思考任何问题。

如果你写过编译器或者用过编译型语言，这个套路会很眼熟：**源代码 → 语法树 → 中间表示 → 优化 → 生成可执行
代码 → CPU 执行**。这里几乎是同一条流水线，只是最后生成的不是机器码，而是一份"怎么算特征"的执行计划。

> **类比**：好比一家做半成品菜的餐厅——大厨在开门营业之前，就把每道菜的菜谱、火候、摆盘顺序都定好、写在
> 单子上；后厨小工上菜的时候只管照着单子操作，不需要现场琢磨"这道菜到底该怎么做"。
>
> 本文后面会反复用**「构建期」**标记"定菜谱"的阶段，用**「运行时」**标记"照单做菜"的阶段。

## 架构总览：五层接力

整套引擎从上到下一共五个阶段，前四个只在服务启动（`init()`）时跑一次，最后一个在每次请求（`generate()`）
时才跑：

```text
        ┌─────────────────── init()：服务启动时只跑一次 ───────────────────┐   ┌── generate()：每次请求 ──┐

  [输入契约] --构建--> [逻辑DAG] --分析--> [只读规划] --编译--> [物理计划] ┊ --执行--> [运行时执行]
 definition/                logical         planning         physical      ┊           runtime
 expression/config                                                          ┊
                                                                     ← 决策全部完成 ｜ 只剩执行 →
```

前四块（输入契约 → 逻辑 DAG → 只读规划 → 物理计划）都发生在构建期，只在服务启动时执行一次；运行时执行由
每一次线上请求触发。两侧只通过一份**不可变的物理计划**交接——运行时看不到、也不需要看到左边任何一层的
分析过程。

横切在五层之上的还有一个 `operator`（算子）包——它定义了"一个算子能做什么"的协议，被逻辑层、规划层、
物理层、运行时共同依赖，但它自己只依赖最基础的语义类型，不反过来依赖任何一层。

## 输入契约层：定义"特征长什么样"

这一层由三个互不依赖的包组成，各管一件事：

| 包 | 负责什么 |
| --- | --- |
| `definition` | 特征的最终定义。造出来就不可变，所有校验在构造的那一刻就做完，绝不允许"半成品"存在。 |
| `expression` | 表达式怎么解析成语法树。这棵树只是构建逻辑 DAG 时的临时工具，用完即弃。 |
| `config` | JSON 配置怎么变成上面的定义。是个适配器，把宽松的外部格式收紧成内部严格的模型。 |

> **类比**：好比装修前的流程——业主口头提的需求（config）先翻译成正式的建筑图纸（definition）；图纸里
> 每个房间具体怎么施工，另有一份临时的施工说明书（expression 的语法树），房子盖完这份说明书就可以扔
> 掉——长期留下来的只有图纸和最终的房子结构。

**两种特征，两条规则**：

| 角色 | 必须 | 禁止 |
| --- | --- | --- |
| `RAW`（原始特征） | 声明所属实体域（USER / ITEM / SCENE…） | 携带任何表达式 |
| `DERIVED`（派生特征） | 携带一段表达式 | 自己声明实体域——最终由逻辑层从表达式推断 |

这两条规则在构造器里就地校验，写错了在造对象这一步就直接报错，不会等到跑起来才发现。

## 逻辑 DAG：只展开真正用得到的部分

这一层从"最终要哪些特征"出发，像剥洋葱一样倒着往回展开每一个依赖，没被用到的特征定义完全不会进图——
这保证逻辑图从一开始就是最小必要子集，不掺任何多余的东西。

**边展开边查环**：展开过程中，每个正在展开的特征都会被打上"进行中"的标记。如果发现要展开的东西自己正
处在"进行中"状态，说明出现了循环依赖（A 依赖 B、B 又依赖 A），会立刻报错，并把完整的循环路径打印出来，
而不是让程序卡死。整棵图搭好之后还会再跑一次拓扑排序做兜底校验——排不进序的节点，就是漏网的环。

**相同的东西只留一份**：同一个原始特征、同一个字面量、同一个"算子 + 同样一组输入"的组合，全图只会保留
一个节点。

> **类比**：两个人在同一份文档里，各自写了一遍 `1 + 2` 这个算式，系统会自动认出这是同一个东西，不会算
> 两遍、也不会占两份内存。

**命名参数在这一层就被"拍平"**：表达式里可以用 `discrete(value: x, boundaries: y)` 这种命名参数写法，
但这只是给使用方的便利。构图之前就会把命名参数按算子声明的参数顺序，归一化成普通的位置参数——后面所有层
（规划、物理、运行时）压根不知道"命名参数"这个概念存在过。

**声明和推断对不上，直接报错**：每个派生特征声明的类型、形状、实体域，都会和从表达式推断出来的结果做
一次比对，对不上就构建失败——唯一开的口子是"声明 DOUBLE、推断出 INT"这一种情况，因为这种场景下，特征
仍然需要对外承诺自己是 DOUBLE（供下游按声明类型定宽）。

## 只读规划：只看一眼、记笔记，不动手

这一层的克制程度是全链路里最高的：它只读遍历逻辑图，为每个节点记三件事，**绝不会把这些笔记写回逻辑图
本身**——这样逻辑图能一直保持干净、只表达业务语义，不会因为"规划需要"而越长越臃肿。

- **被引用几次**：判断这个节点是不是"共享"的，共享的东西不能被后面的优化随意合并掉。
- **能到达哪些目标**：这个节点的结果，最终会影响到哪些输出特征。
- **能不能缓存**：来自算子自己的声明——确定性 + 无副作用，两条都满足才允许缓存。

> **类比**："能到达哪些目标"这件事，如果给每个目标特征都各自反向遍历一次共享的祖先节点，重复遍历的开销
> 会随着目标数量线性增长。这里换了个顺序：先按拓扑序把图从后往前走一遍，每个节点在自己和它所有"下家"的
> 答案都确定之后，才把这个答案的并集传给自己的"上家"——相当于快递从最后一个收件点开始，把沿途所有该带
> 的信息一次性顺路捎带上去，而不是为每个目标各跑一趟。

## 物理计划：把"该怎么做"写成一份死清单

这是构建期干活最多的一层，做三件事：

1. **识别可以合并优化的模式**（融合）：把"先做 A 再做 B"这种低效的通用路径，换成一个专门写好的高效
   算法。
2. **给每个节点定死执行细节**：什么时候跑（离线整批 / 在线请求共享 / 在线候选批）、要不要缓存、算子走
   单值还是批量。
3. **产出一份不可变的执行计划**：运行时只管照着执行，不再重新判断任何一件事。

**四种通用节点，各自对应一种执行器**：

| 逻辑节点 | 物理执行器 | 做什么 |
| --- | --- | --- |
| 源节点 | `SOURCE_BINDING` | 绑定外部输入名、默认值、所属实体域 |
| 字面量 | `LITERAL` | 直接携带常量值 |
| 算子节点 | `GENERIC_OPERATOR` | 记录该走 Single 还是 Batch Kernel、序列要不要零拷贝直传 |
| 特征输出边界 | `FEATURE_OUTPUT` | 要不要把整型结果定宽成 DOUBLE，这里就已经定死 |

三类关键策略也在这一步一次性定死，而且**只依据环境、实体域、算子自己声明的能力来推导，绝不允许按"这个
算子叫什么名字"来写 if/else 特判**——这是保证系统可以持续新增算子、而不用去改核心代码的关键。

## 融合实例：把两步合并成一步

用一个具体例子说明"融合"到底在优化什么。假设表达式先按 key 过滤一个序列，再统计过滤后剩几个元素：

```text
未融合：按通用路径逐节点执行

用户序列 ──▶ 按 key 过滤 ──▶ [中间序列（整份物化）] ──▶ 计数 ──▶ 结果


融合后：命中规则，替换为专用执行器

用户序列 ──▶ SequenceKeyCountExecutor（建一次索引 → 直接查 count，不产生中间序列） ──▶ 结果
```

输入、输出完全相同，消失的只有中间那次整份物化和第二次遍历。"先过滤、物化中间序列、再遍历计数"其实是
同一个算法的两次求值。融合规则识别出这种 DAG 模式后，用一个专用执行器（先建 key 索引、再查计数）一次性
完成，中间那份被物化又立刻被扔掉的序列彻底消失。

能不能融合，靠的是构建期规划层记下的两条笔记：中间节点必须**不是最终输出**、并且**只被引用了一次**
（否则它被别处共享，合并会悄悄改变别处看到的结果）。这些安全边界的判断，全部发生在服务启动时，运行时
不需要、也没有能力重新验证。

## 运行时执行：照单全收，只管跑

物理计划规定的顺序是什么，运行时就按什么顺序，一个节点接一个节点地跑；每个节点的结果写进它专属的
"格子"（槽位），后面的节点从格子里取数据——运行时唯一的工作就是"照单执行"，不重新判断该不该缓存、该走
单值还是批量、该不该融合。

**结果值的几种打包方式**：每一步算出来的结果都被包在一种固定的"值句柄"里，运行时用穷举类型（等价于其他
语言里的联合类型/枚举）把所有可能的打包方式列全，编译器会强制每一处用到它的代码都把每种情况处理到：

- `ScalarValue` —— 一个普通标量值
- `SequenceValue` —— 一段序列（可能是零拷贝的视图）
- `IndexValue` —— 一组下标集合
- `OfflineBatchValue` —— 离线场景：一整批输入行
- `RequestBatchValue` —— 在线场景：一批独立请求组的共享值
- `CandidateBatchValue` —— 在线场景：展平后的一批候选值
- `CandidateVectorValue` —— 单次在线请求内的候选向量

## 单值还是批量：由拿到的数据形状决定

逻辑图里的算子永远只表达"给一个值，算一个值"的单值语义；"这次要不要批量处理"完全是运行时的事，算子
本身并不需要关心。运行时看这次拿到的输入是普通标量，还是打包过的批容器，据此二选一：

```text
                算子节点执行
                     │
              看这次输入类型
              ┌──────┴──────┐
              ▼             ▼
         标量输入        批容器输入
        Single Kernel    Batch Kernel
                        （原生实现 或 逐行适配）
```

走 Single 还是 Batch，是根据这次实际拿到的输入载体类型做的固定分派，不是重新做物理决策。Batch 那一支
还要再分两种：算子自己写了专门的批量实现（原生），或者由框架提供的通用逐行适配器代劳。

**批量必须和单值逐行一模一样**：不管走哪条路径，批量结果的第 `i` 行必须和单独调用单值版本处理第 `i`
个输入得到的结果完全一致，行数不能变、顺序不能变，这是一条硬约束——批量只是换了个更省事的算法/更少的
调度开销，不能改变结果本身。

16 个标准算子里，只有 `find_indices`、`count_distinct`、`zip_concat`、`calc_delta_seq` 这 4 个自己写了
原生批量实现——因为实测下来，这几个算子在一批数据里有明显可以复用的中间结果。其余算子实测发现"攒批"的
开销比省下来的计算量还大，索性老老实实逐行算，不强行凑批量。

**序列不用来回复制**：如果一个算子声明自己能直接处理序列的"视图"（而不需要一份完整复制出来的
List），运行时就会把这份视图原样传给它，同一批里出现多次的同一段具体序列，也只会真正物化一份。这一点
在构建期就已经根据算子的声明定死，不是运行时临时判断。

## 算子体系：新增能力不改核心代码

每个算子独立成一个文件，自己声明参数个数、是否确定性、是否有副作用、能不能直接吃序列视图；注册表只
负责"认识这些算子、按名字查、校验参数个数"，不承载任何业务逻辑。这样新增一个算子，只需要新写一个文件、
注册进清单，完全不用碰逻辑层、规划层、物理层、运行时的任何代码。

| 类别 | 算子 |
| --- | --- |
| 首期业务算子（8 个） | `discrete` `log_base` `slice_by_indices` `find_indices` `get_seq_length` `count_distinct` `zip_concat` `calc_delta_seq` |
| 数值转换 / 极值 / 算术（8 个） | `to_int` `to_bigint` `min` `max` `add` `sub` `mul` `div` |

业务方也可以在初始化时注册自己的扩展算子，走的是和内置算子完全一样的注册、推断、执行路径。

## 对外入口：两阶段使用

整套系统对外只暴露一个类、两个动作：

- **`init()`**：读配置，逐层构建出物理计划，并在这一步就校验完所有专用执行器——让配置错误在启动时
  暴露，而不是等第一个线上请求来了才炸。
- **`generate()`**：解码输入 → 运行时执行 → 编码输出，三段各自计时，支持离线单行、离线整批、在线单
  请求、在线分组批四种请求形态。

`demo` 包里有三个可以直接跑起来的调测入口，全部通过这套公共 API 调用，方便不熟悉源码的人先跑一遍、看看
输入输出长什么样，再回头看具体某一层的实现。

## 为什么部分代码故意写得像旧版本 Java

整个仓库按 Java 21 构建，但首期 8 个业务算子、它们共用的支撑代码，以及首期 Demo，被刻意限制只使用
Java 8 就能跑的语法（不用 `record`、不用模式匹配、不用新版集合工厂方法）。

这不是为了让整个仓库能在 JDK 8 下编译——事实上核心层大量用了 `record`、`switch` 表达式这些新特性。这么
做单纯是为了让这一小撮算子代码保持"轻装上阵"：将来想把它们单独抽出来复用，或者用代码生成的方式批量产出
新算子，不会被高版本语法特性绑住手脚。

## 贯穿全链路的十条法则

仓库的贡献指南 `AGENTS.md` 里把这些约束编号为 C1–C10；翻译成人话，大致是这样：

| 编号 | 法则 | 人话解释 |
| --- | --- | --- |
| C1 | 依赖只能单向流动 | 输入契约 → 逻辑 → 规划/物理 → 运行时，后面的层永远不能反过来改前面的产物。 |
| C2 | 造出来就不能改 | 特征定义在构造器里一次性校验完，不存在"半成品"状态。 |
| C3 | 只展开用得到的 | 逻辑图从目标特征出发倒着构建，没被引用的定义完全不会进图。 |
| C4 | 环在构建期就被抓住 | 三色标记 + 拓扑排序兜底，循环依赖不可能跑到线上才发现。 |
| C5 | 相同的东西只留一份 | 按签名去重，同一个字面量、同一次算子调用全图只算一遍。 |
| C6 | 声明必须和推断对得上 | 唯一放宽的口子：声明 DOUBLE、推断 INT。 |
| C7 | 节点之间只认 ID，不认对象引用 | 依赖关系通过节点 ID 和端口连接，保证逻辑图可以安全地整体不可变。 |
| C8 | 规划只读，不许回写 | 引用计数、可达根、缓存资格全部记在外部元数据表里，不污染逻辑节点。 |
| C9 | 融合有安全线 | 被合并的中间节点必须非最终输出、且只被引用一次。 |
| C10 | 决策在编译期，执行在运行时 | 执行阶段、缓存策略、单值/批量路由全部构建期定死；核心代码禁止按算子名字写 if/else。 |
