# 在线列式接口性能基线

使用 PR #50 实现提交 `564e590ece13c3ea409a7451e8392a60cdcaf577`，在同一版本中比较现有行式入口与新增列式入口。原始数据见 [JSON](online-columnar-baseline.json)。

## 方法与计时边界

- 使用现有 `LargeOnlineWorkload(512, 300, 8)`：320 BASE、320 DERIVED、300 候选、8 组循环输入；160 个共享序列长度 512，候选输入为 80 个标量特征。未覆盖候选长序列场景。
- 三种模式各 3 个独立 JVM，每次预热 15 秒、测量 20 秒；轮换执行顺序，单线程串行调用，关闭观测。每个 JVM 测量前校验全部 8 组输入的新旧输出等价。
- Java 21.0.13+9，`-Xms2g -Xmx2g -XX:+UseZGC -XX:ActiveProcessorCount=4`。ActiveProcessorCount 是 JVM 配置，不代表独占或绑定 4 个物理核；运行环境不是生产机器。
- 计时包含请求对象构造、输入解码、DAG 执行及结果构建；输入预先准备。行转列、业务映射、拆分、网络和业务结果回写不在计时内。这是引擎入口对比，不是服务端到端压测。
- `row-snapshot` 使用旧请求普通构造器；`row-borrowed` 使用旧请求 borrowed；`column-borrowed` 使用新增列式请求 borrowed。列式与行式 borrowed 的比较更能体现结构差异；与 snapshot 比较还包含快照复制开销的差异。未测试列式快照构造器。
- 分配量由 ThreadMXBean 统计调用线程累计分配字节/请求，使用十进制 MB；不代表堆存活量、RSS 或所有线程分配量。
- 独立 main 基准，不是 JMH；不把性能阈值放进单元测试。短测量窗口及共享环境噪声限制了结论。

## 三轮各指标的中位数

下表是每个 fork 指标的中位数，P95/P99 不是合并全部请求后的分位数。

| 模式 | QPS | P50 ms | P95 ms | P99 ms | 分配 MB/请求 |
|---|---:|---:|---:|---:|---:|
| row-snapshot | 49.61 | 19.794 | 23.782 | 26.729 | 43.803 |
| row-borrowed | 48.52 | 18.894 | 24.589 | 33.640 | 37.492 |
| column-borrowed | 54.39 | 16.786 | 29.092 | 33.015 | 36.377 |

## 列式相对旧入口的变化

| 对比基线 | QPS | P50 | P95 | P99 | 分配量 |
|---|---:|---:|---:|---:|---:|
| row-snapshot | +9.63% | -15.20% | +22.33% | +23.52% | -16.95% |
| row-borrowed | +12.10% | -11.16% | +18.31% | -1.86% | -2.97% |

列式 borrowed 的 P50 与串行吞吐量改善；相对行式 borrowed，分配量仅下降约 3%，P95 反而升高约 18%。因此本轮不能得出“列式全面降低延迟”或满足生产尾延迟目标的结论。三个 fork 的波动明显，尤其行式 snapshot P99 为 25.36–49.15 ms；尚未通过 CPU/GC profile 隔离原因，不能把差异直接归因于 GC 或结构本身。

## 复现

在 Java 21 与 Maven 可用的环境执行：

```bash
bash scripts/run-columnar-benchmark.sh
```

输出位于 `target/columnar-baseline/`。性能入口为 `src/test/java/com/example/featuredag/performance/ColumnarOnlineBenchmark.java`。

下一步如要判断上线收益，应在目标机器使用实际输入分布、生产 JVM 参数、更长测量窗口及真实并发复测，并同时采集分配和 GC/CPU profile；优先确认 P95/P99，再决定是否切换调用。
