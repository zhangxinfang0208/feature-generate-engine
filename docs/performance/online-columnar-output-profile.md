# 列入列出性能基线与 GC/JIT/CPU 诊断

2026-11-05。新增 `generateColumnarResult(OnlineColumnarGenerateRequest)`，直接从候选向量生成特征列；旧接口不变。

## 结论

普通基准三轮中位数：相对旧行式 borrowed，列入列出的 P95 降低 20.57%、P99 降低 24.03%、进程 CPU 时间/请求降低 21.69%、调用线程分配量/请求降低 25.50%。相对列入行出，P95 降低 15.51%，分配量降低 23.18%。本轮完整列式路径更符合下游直接消费列的需求；结果不等于生产 SLA 保证。

## 普通基准（不启用 JFR）

各指标是三个独立 JVM 的中位数，不是合并请求分位数。GC 日志在所有模式使用相同设置。

| 路径 | P50 ms | P95 ms | P99 ms | QPS | 分配 MB/请求 | 进程 CPU ms/请求 |
|---|---:|---:|---:|---:|---:|---:|
| 旧行入行出 borrowed | 18.328 | 23.663 | 31.901 | 52.57 | 37.510 | 21.274 |
| 列入行出 borrowed | 17.041 | 22.245 | 27.539 | 56.48 | 36.376 | 19.770 |
| 列入列出 borrowed | 14.923 | 18.795 | 24.235 | 64.85 | 27.945 | 16.660 |

这里的旧行式基线没有额外做行转列，对旧接口是偏有利的比较；不包含业务映射、序列拆分、网络和结果回写。测量包括请求对象构造、引擎执行及编码。分配 MB 为十进制 MB，来自调用线程累计分配，不是 RSS/存活堆；CPU 时间包含整个 JVM 进程的线程，不等同于墙钟耗时。

## GC 与 JIT（单独诊断轮次）

JFR 在预热前启用；以下只统计测量请求时间窗口内的事件。GC 周期包含并发阶段，不是 STW；编译事件累计时长也不是请求停顿。

| 路径 | GC 周期数 | GC 暂停总计 ms | 最长暂停 ms | 分配停顿事件 | JIT 次数 | 编译事件累计 ms |
|---|---:|---:|---:|---:|---:|---:|
| 旧行入行出 borrowed | 34 | 1.165 | 0.120 | 0 | 114 | 300.0 |
| 列入行出 borrowed | 38 | 1.250 | 0.110 | 0 | 121 | 298.1 |
| 列入列出 borrowed | 31 | 0.942 | 0.046 | 0 | 108 | 185.2 |

慢请求按每个诊断轮次请求事件 P95 划分。下表为与 GC 周期重叠的比例；重叠是相关性，不能直接证明 GC 导致这些请求变慢。

| 路径 | 全部请求与 GC 重叠 | 最慢 5% 与 GC 重叠 | 最慢 5% 与编译重叠 |
|---|---:|---:|---:|
| 旧行入行出 borrowed | 175/1367 | 40/69 | 3/69 |
| 列入行出 borrowed | 201/1662 | 49/84 | 2/84 |
| 列入列出 borrowed | 173/1819 | 50/91 | 3/91 |

## CPU 栈采样

JFR ExecutionSample 按栈中出现的解码器、输出编码器或 DagRuntime 分类；是 Java 执行样本占比，不是精确的分阶段计时，也不覆盖所有原生线程 CPU。完整热点列表见 JSON。

| 路径 | 样本数 | 解码 | Runtime | 输出编码 | 其他 |
|---|---:|---:|---:|---:|---:|
| 旧行入行出 borrowed | 1201 | 6.5% | 60.6% | 27.3% | 5.6% |
| 列入行出 borrowed | 1104 | 0.0% | 62.6% | 37.2% | 0.2% |
| 列入列出 borrowed | 1016 | 0.1% | 71.9% | 27.4% | 0.6% |

诊断结论：

- 列入列出在 30 秒测量窗口内发生 31 次 GC，总暂停约 0.942 ms，最长暂停约 0.046 ms，没有 ZAllocationStall。直接 STW 或分配停顿不能解释该轮数毫秒级尾部差异。
- 该路径最慢 5% 请求有 50/91（54.9%）与 GC 并发周期重叠，而全部请求为 173/1819（9.5%）。并发回收相关的资源竞争是下一步值得验证的方向，但还没有线程调度/原生 CPU 数据证明因果。
- 该路径测量窗口有 108 次编译、累计事件时长约 185 ms；最慢请求仅 3/91 与编译重叠，耗时最高的编译是 JFR 元数据写入。当前数据不支持把业务尾延迟主要归因于 JIT。
- 列入行出的输出编码样本占比约 37.2%，列入列出约 27.4%；列入列出约 72.0% 的执行样本在 Runtime。剩余主要热点包括 `SliceByIndicesOperator.slice`、`SingleLoopBatchOperatorKernel.evaluateBorrowedArguments`、元素级算子求值，以及序列输出物化。下一步应针对这些实际热点优化，而不是继续只改输入容器。

## 为什么列式输出能减少开销

此 workload 有 320 个候选输出，其中 280 个标量、40 个序列。旧输出为 300 个候选构建逐行 Map，写入约 96,000 个特征条目，并对约 84,000 个标量构造单元素 List。新增入口生成 320 个输出列，标量直接写入列；保留序列物化、截断/补齐以及运行时向量原有防御复制。输入列式化只优化入口，此次同时减少输出端容器和包装，这与实测分配量下降方向一致。

## 采集干扰与结论边界

最初曾在测量开始时启动 JFR，出现大量编译和明显采样扰动（列入列出诊断 P95 约 25.54 ms，普通轮次中位数 18.80 ms）。因此把 JFR 启动提前到预热前，补跑三组诊断。诊断数据绝不混入普通基准中位数；采样轮次仍可能扰动执行，不用它的耗时替代性能基线。

上一轮的“列入行出 P95 上升 18.3%”没有当时的 JFR，本轮不能追溯确定其原因；本轮同批比较的列入行出 P95 为 22.24 ms，低于旧行式的 23.66 ms，说明旧观察没有稳定复现。不能把历史差异全部归因于 GC 或 JIT。

## 方法与复现

- Java 21.0.13+9；`-Xms2g -Xmx2g -XX:+UseZGC -XX:ActiveProcessorCount=4`。运行容器观测到 8 CPU 配额、8 GiB 内存限制，非独占生产机器，ActiveProcessorCount 不表示 CPU 绑核。
- `LargeOnlineWorkload(512,300,8)`：320 BASE、320 DERIVED、300 候选、160 个共享序列（长度 512）、80 个候选标量输入、8 组轮转输入。未覆盖候选长序列输入或完整业务链路。
- 普通三轮轮换顺序，诊断每模式一轮；每 JVM 预热 20 秒、测量 30 秒，单请求串行。不是生产并发容量测试或 JMH 置信区间分析。
- 全部模式复用同一引擎实现；功能测试以 8 组大 workload 校验列式结果与旧接口等价。
- 性能数据基于 PR #50 的实现增量，源码哈希及每轮原始指标保存在 JSON。普通轮次之后仅将诊断录制启动移到预热前，业务执行路径和普通计时循环不变。

```bash
bash scripts/run-columnar-profile.sh
bash scripts/export-columnar-jfr.sh
```

第二个脚本导出选定事件并分析。诊断 JFR 可用 JDK Mission Control 打开，保留 CPU 样本、GC、JIT、分配采样和请求时间线。JSON 导出选择主要诊断事件以控制大小，JFR 中有更完整的事件。
