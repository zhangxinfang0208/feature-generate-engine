# Configuring Feature DAG Models

Use this instruction-only workflow for business configuration. It performs rule validation, never invents missing feature semantics, and does not imply engine execution.

## Business-facing dialogue

Before processing any request, read [business dialogue](references/business-dialogue.md). Every user-facing response uses its short Chinese text template for the one active step. Render explanatory text as ordinary Markdown; fence only copyable JSON, never the whole response. Do not expose internal stage objects, protocol versions, empty arrays, validator state, or a machine-oriented JSON envelope. Keep fixed labels and section order identical on Codex, Claude Code, and every other host. Use JSON only for frontend additions and for examples the business can copy.

1. **Syntax intake — read [expression grammar](references/expression-grammar.md).** Take one expression and the business-provided DERIVED name when available. Accept the business shorthand `derived_name=expression` and parse only its right-hand expression. Preserve `original_input` and `normalized_input` internally; if no string-external `\_` exists, they must be identical. Normalize eligible `\_`, report that notice only when it occurred, then parse syntax. Audit the exact normalized character stream with an immutable `<EOF>` boundary and delimiter stack; keep `<EOF>` out of the expression and never append or repair tokens. On an error, stop and use only the syntax-correction dialogue; do not request BASE metadata.
2. **BASE discovery — read [expression grammar](references/expression-grammar.md).** After successful syntax, extract ordered, first-seen unique feature references from the AST; do not treat operators, argument names, object keys, or strings as features. Accept either a BASE-only `features` array or a full model configuration. Select needed entries by exact `name`, ignore unrelated entries, and keep AST first-seen order. If any referenced BASE entry is absent, stop and request only those current frontend entries. Do not ask for field values yet.
3. **BASE completion — read [feature fields](references/feature-fields.md).** Only after receiving the current frontend entry for every referenced BASE, check each entry feature by feature. Batch all unresolved facts into one business-friendly text request and include a directly editable reply example grouped by feature. Treat absent `definition_type=BASE` and `to_use=true` as deterministic additions rather than business questions; contradictory populated values are conflicts. Emit additions only after the business supplies other unresolved facts; never infer them from a BASE name or expression.
4. **DERIVED completion — read [operator contracts](references/operator-contracts.md).** Only after syntax succeeds and semantic inference is needed, apply available contracts. Use `DERIVED` as the definition type for derived entries. Emit every absent field that the contract determines exactly—even during final validation before reporting `FAIL`. Operator names alone do not determine shape: for example, `add(...)` has scalar `seq_max_length` `1` only when all inputs are scalar, and produces a sequence when any input is a sequence. Emit numeric additions without quotes. Ask the business only when the contract or inputs leave the value unresolved. A missing contract is `INCOMPLETE`, not a claim about registration or legality.
5. **Final validation — read [validator extension](references/validator-extension.md).** Enter this stage only when the business explicitly submits the filled model for final validation, with a named target and complete `{feature_set_name, version, features}` wrapper. A full configuration supplied as current BASE metadata remains BASE input even if it includes `feature_set_name` and `version`; extract the needed BASE entries and do not validate the model. For a final submission, validate the named target and recursively reachable dependencies only. Prefer a compatible available validator; clearly disclose rule-validation fallback.
6. **Verdict — read [output contracts](references/output-contracts.md).** For a gated wrapper, return `FAIL` for reachable declaration/reference/conflict/duplicate/cycle errors before considering `INCOMPLETE`; use `INCOMPLETE` for unavailable facts/contracts, and `PASS` only for a complete reachable graph. If a remote validator ran, label the result as a remote result; if the workflow fell back to rules, label it as rule validation only. Unrelated model entries and non-engine fields are out of scope. Before the final-validation gate, do not return an early final verdict.

Use [feature fields](references/feature-fields.md) whenever a step compares declarations, scopes, shapes, defaults, or reachability. Use [output contracts](references/output-contracts.md) whenever emitting additions or a model wrapper. Object-valued additions are information gaps rather than guessed or malformed JSON. Before sending the response, self-check that it follows exactly one dialogue template, requests the current BASE configuration before missing facts, groups work by feature, and preserves the five-key frontend property format.
